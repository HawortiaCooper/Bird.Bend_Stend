# Gate runner (D-57) — design note

| Doc | GATE_RUNNER |
|---|---|
| Version | 1.2 (2026-10-14) — C's re-review C-GR-4 / C-GR-5: a board session stops when any item ends with the device unidentified and refuses to start a non-identity item while it is unidentified; HG-15 power cycle re-identifies. 1.1 (2026-10-14) — GR-2 plain-language prompts and the final pictures B1–B9 (GR-3); bench facts verified at S-00 (GR3-2); C's review C-GR-1…3 (approved options only, analysis anchors, whole-bundle runner hash); design limits (a) revocation, (b) results-zip anchor. 1.0 — first version |
| Owner | Validator E (00_System/tools/hil; the Integrator reviews independently). Packaging: B. Pictures: A. Approval files: Orchestrator |
| Basis | D-57 (PO: operator alone, frozen runner), D-06, D-41, D-42, D-45, D-52, D-56; FW_test_plan v0.4.13 §6 / §6.7 / §6.8; HW_GATE_RUNBOOK v0.4 |

The formal hardware gate (HG-01…HG-32) is run by the PO's operator alone with a frozen copy of the existing HIL
session (`hil_session.py`). The runner needs no repository and no Python. It refuses before any port is opened unless
an approval file generated by the Orchestrator matches it. It writes one results zip, which Validator E evaluates
offline (`hil_analyze.py`) before writing `FW_test_report_HG1`. Agents never run it against hardware (D-06).

## 1. Entry point, inputs, outputs

**Entry point:** `00_System/tools/hil/gate_runner.py` → `main()`, frozen as **`BirdBendStand-GateRunner.exe`**
(console, PyInstaller one-folder). The packaging agent places it in the gate kit as
`04_Delivery/GateKit_FW<rel>/BirdBendStand-GateRunner/`.

| Command | Purpose |
|---|---|
| `BirdBendStand-GateRunner.exe` | no arguments: asks for the approval file, the COM port and the output folder |
| `… --approval <file> --port COM7 --out <folder> [--from HG-28] [--only …]` | board session (resume with the same `--out`) |
| `… --twin --out <folder> [--quick]` | rehearsal on the bundled FW twin; no board, no approval needed, never evidence |
| `… --verify-zip <results zip>` | integrity check of a results zip (manifest, sizes, hashes) |
| `… --version` / `… --list` | runner identity (name, version, SHA-256) / the ordered plan |

**Inputs (all outside the repository):**
- the approval file (§3);
- the kits it names (`--delivery`, default = the folder above `GateKit_FW…`: the gate images in the gate kit, the
  release image in `BringUp_FW…/firmware`);
- the operator's answers;
- the board on the named port.

**Bundled resources** (`gate_res.py`; packaging copies them in):

| Bundle path | Source in the repository | Use |
|---|---|---|
| `resources/params.yaml` | `00_System/specs/params.yaml` **of the approved commit** | dictionary hash (identity check S-00, R-HIL-01) |
| `resources/pictures.json` | `00_System/tools/hil/resources/pictures.json` | prompt → picture map (§5) |
| `resources/prompts_plain.json` | `00_System/tools/hil/resources/prompts_plain.json` | plain-language prompt texts (§5, GR-2) |
| `resources/pictures/*.png` | `01_HW/diagrams/bench/B1…B9*.png` (README v1.1) | prompt pictures |
| `fw_twin/fw_twin.exe` | twin built from the **same commit** (`00_System/tools/fw_twin/build.py`) | `--twin` rehearsal only |

Python modules: `gate_runner`, `gate_res`, `gate_approval`, `gate_export`, `hil_session`, `hil_procs`, `hil_link`,
`hil_budget`, `hil_operator`, `hil_report`, `ref_codec`, `gen_params`, `gen_protocol`, `twin`, `build`.
Hidden imports: `serial` (pyserial, imported only after the interlock), `yaml`.

**Outputs:** only below `--out` (standing data rule; enforced by `test_stray_run_writes_only_into_its_output_folder`):
- `session.json`, `results/<item>.json`, `HG_report_<mode>.md`;
- `prompts.jsonl` (every answer, UTC);
- `raw/frames.bin` (raw frame log);
- `approval.json` (copy of the approval file), `runner.json`;
- `twin_run/` (rehearsal only);
- the results zip `gate_<YYYYMMDD>_<UID>_<session>.zip` (§4).

The operator can drop photos into `<out>/photos/`; a later `--from` run re-exports the zip.

**Runner identity** (`gate_res.runner_identity`, C-GR-3):
- **frozen:** SHA-256 over the executable **and every file below the bundle root** `_internal/` (Python runtime,
  libraries, `base_library.zip`, `resources/`, `fw_twin/` — path + content, sorted) (`bundle_sha256`). At run time the
  bundle root is `sys._MEIPASS` (= `_internal`), in `make_approval.py --runner-exe` it is the `_internal` folder next to
  the executable, so both compute the same value. **A one-folder build is required** (a one-file exe has no
  `_internal` next to it; `make_approval` refuses it);
- **source run:** SHA-256 over the runner's source files, the picture map and the plain-text map.

`--version` prints it.

## 2. Interlocks (unchanged in substance, now repository-free)

- **D-06:** a port is opened only through `hil_link.open_serial()`, after the approval file passed every check (§3)
  and the operator re-typed the port name.
  - The validity window is re-checked at every (re)open, e.g. after each flash.
  - In the frozen runner a reference string (the old `--approved`) is refused outright.
  - The session CLI no longer reads DECISIONS.md / STATUS.md; `make_approval.py` applies those rules once, when the
    Orchestrator generates the file.
- **Identity:**
  - **S-00:** GET_INFO dict hash = bundled `params.yaml`; protocol 1.0 / payload 1; UID = the approval file's
    board UID. The image kind comes from the build suffix and FEAT_HW_MEAS, **and the build string must equal the
    approved image's build string**.
  - **S-ID:** the same check on a resume.
  - Any mismatch stops the session. Nothing (no HALT / HALT_CLEAR) is sent to an unidentified device (C-R3).
  - **Every port re-open re-identifies** before anything else is sent: the image steps, the HG-01 / HG-20 USB-off
    block and the HG-15 power cycle (C-GR-5) mark the device unidentified before closing the port and run the identity
    check right after the re-open.
  - **Session rule (C-GR-4, belt and braces):** in a board session, any item that ends with the device unidentified
    stops the session (rc 2), and no item other than S-00 / S-ID / IMG-* may start while it is unidentified. BENCH-EXIT
    is sent only to an identified device; otherwise the runner prints the manual restore (48 V OFF; if the sense was
    bypassed: remove J-STIM, reconnect the sense plug, remove the tag, §6.8 P-8) and the operator reports.
- **Bench and load gates:** BENCH-ENTRY directly before and BENCH-EXIT directly after HG-10a; a failed BENCH-ENTRY
  runs BENCH-EXIT first. GATE-LOAD comes before phase 4. Results count only from the current session.
- **Flashing:** every prompt names the approved `.hex` file with its build string and SHA-256 prefix:
  STM32CubeProgrammer, method B2, never the `.bin`, never a full-chip erase (picture B5).
- **Accepted-open items** (§6.6) come only from the approval file.
- **Session options (C-GR-1):** a board session refuses `--quick`, `--seed`, `--counts-per-n`, `--buffer-fitted`,
  `--power-sense-fitted` with a non-default value unless the approval file pins that option with the same value
  (`options`, written by `make_approval.py --option key=value` only when the Orchestrator asks for it); pinned options
  apply even when not typed. `session.json` records the effective options and which were pinned.

## 3. Approval file (JSON) — replaces the DECISIONS.md lookup

Generated by the Orchestrator with `make_approval.py`, checked by `gate_approval.check()` before any port.

| Member | Content | Runner check |
|---|---|---|
| `schema`, `schema_version` | `bird.bend.gate_approval`, 1 | exact |
| `reference` | `D-06-GATE-YYYYMMDD[-TAG]` | format, real date |
| `decision_row` | the dedicated row of DECISIONS.md / STATUS.md, verbatim | first cell = reference, last cell `approved` / `approved (PO)`, no negation / question / open state (FWR-12), **names the board UID** |
| `board_uid` | 24 hex digits | format; = optional `--board-uid`; = GET_INFO UID at S-00 / S-ID |
| `valid_from`, `valid_until` | dates, inclusive | `valid_from` = reference date; window 0…7 days; today inside it (at every port open) |
| `kit.images.{release, meas, meas_dwt}` | `path` (relative to the delivery folder, `.hex` only), `sha256`, `build` (GET_INFO build string) | file present and SHA-256 equal; the board's build = `build` of the image kind |
| `kit.commit`, `kit.fw_version`, `kit.param_dict_hash` | from the kits' BUILD_INFO.txt | dict hash = the runner's `params.yaml` |
| `runner.{name, version, sha256}` | the frozen runner of the gate kit | = this runner's identity |
| `accepted_open[]` | `{item: HG-xx, ref, row}` | format; the row is an accepted row naming the item |
| `evidence.tc_sys_009_02` | `PASS — <BUILD_INFO line>` | used by HG-29 f instead of reading FW_test_report_M2 |
| `options` (optional) | pinned session options: `quick`, `seed`, `counts_per_n`, `buffer_fitted`, `power_sense_fitted` | known keys and types; the only way a board session uses a non-default option (C-GR-1) |
| `generated_by` | tool, version, UTC, repo commit, by | present |
| `body_sha256` | SHA-256 of the canonical JSON (sorted keys, no spaces, UTF-8) of every other member | equal — otherwise "edited or damaged" |

**Refusals** (each ends the run with `REFUSED: …`, exit 2, before the session folder or a port is created):
- file missing or not JSON;
- wrong schema;
- body hash mismatch (tampered);
- reference not well-formed;
- row not approved, not dedicated, or not naming the UID;
- window wrong, not yet valid or expired;
- UID cross-check fails;
- runner hash differs;
- dictionary hash differs;
- image missing, not `.hex`, or its hash differs;
- accepted-open entry not accepted;
- `--approved`, or `--accepted-open` given on the command line;
- a non-default session option not pinned by the file (C-GR-1).

**Generation** (Orchestrator, repository):
`make_approval.py --ref D-06-GATE-… --board-uid … --runner-exe <kit>\…\BirdBendStand-GateRunner.exe
[--accepted-open HG-xx:REF …] --out approval_<ref>.json`. It uses hil_link's rules:
- dedicated approved row, ≤ 7 days old, not in the future;
- C-R1 (any other row for the reference that does not approve it cancels it);
- C-R2 / C-R4 (rows inside fences or indented blocks don't count);
- FWR-12 / FWR-13 (negation, accepted-open rows).

It also checks every `.hex` against its kit's `SHA256SUMS.txt` and takes the build strings, commit, dictionary hash
and TC-SYS-009-02 line from the kits' `BUILD_INFO.txt`.

**GR-5 (decided):** `make_approval.py` prints a ready-to-paste row for `00_System/specs/GATE_APPROVAL_LOG.md`
(Orchestrator-owned):
`| issued UTC | body SHA-256 | D-06-GATE ref | board UID | kit commit | runner hash | issued for |`.
- The first cell is the issue time, never the reference, so a log row can never be read as an approval record (C-R1).
- The approval-row parser reads only DECISIONS.md / STATUS.md (`hil_link.APPROVAL_FILES`); test
  `test_log_row_is_never_an_approval_record` covers this.

The file itself is not secret, so the runner can only detect edits. **Authenticity is checked offline:**
`hil_analyze.py <zip> --approval-log 00_System/specs/GATE_APPROVAL_LOG.md`. It looks up the zip's approval body hash
in the log and compares reference, board UID, kit commit and runner hash with that row. `--approval-sha <hash>` is
the manual alternative.

## 4. Results zip

`gate_<YYYYMMDD>_<board UID | twin>_<session id 8>.zip`, written by `gate_export.export()` into `--out` at the end of
every run (also after a refusal inside the session or an abort), atomically. **Tamper anchor (design limit b):** the
runner then prints the zip's SHA-256 in a framed block ("SEND THIS LINE TO THE PRODUCT OWNER NOW, SEPARATELY FROM THE
ZIP") and writes the same line to `<out>/zip_sha256.txt`; the operator sends that line at once, e.g. in the message
text, and the zip separately.

| Member | Content |
|---|---|
| `manifest.json` | `bird.bend.gate_results` v1: session id, mode, board UID, approval reference + body hash, runner identity, kit images (path, SHA-256, build), created UTC, `files[]` = `{path, size, sha256}` of every other member |
| `session.json` | session metadata (plan order, images seen, seed, approval, runner) |
| `results/<id>.json` | per item: checks (`name`, `criterion`, `decision`, `value`, `unit`, `u`, `budget`, `n`, `stats`, `note`), raw data (`data`: trials, probe reads, DWT sections, …), operator answers, session binding |
| `HG_report_<mode>.md` | the human-readable report |
| `prompts.jsonl` | every prompt answer: item, key, prompt, value, source (`operator` on the bench), local and UTC time |
| `raw/frames.bin` | raw frame log, header `BBSRAW1\n`, records `<QBI` (t_ns, direction 0 = PC→FW / 1 = FW→PC, length) + bytes |
| `approval.json`, `runner.json` | the approval file the session ran under; runner identity, Python / OS, command line, kit hashes verified |
| `photos/…` | operator photos (optional) |

`gate_export.verify()` (also `--verify-zip`) checks four things:
- the manifest is present;
- every listed member is present with its size and SHA-256;
- no member is unlisted;
- no path escapes the archive root.

**Offline analysis** (`hil_analyze.py <zip> --approval-log <GATE_APPROVAL_LOG.md> | --approval-sha … --zip-sha "<line the operator sent>" [--runner-sha …] --out draft.md`):
1. Integrity.
2. Provenance: approval hash (content = manifest = recorded), runner hash = the approval's, results bound to this
   session and board.
3. Re-evaluation of every measured check from its recorded value / budget / u (§6.1 rule 4, `hil_budget`; DWT from
   the raw-max note). A re-evaluated decision that differs is listed as a MISMATCH.
4. Raw frame log parsed with the reference codec (frames per direction, CRC / length errors, time order).
5. Answer sources (a board session must contain operator answers only).
5a. Board-zip rules (C-GR-2) — each is a PROBLEM: no approval anchor (`--approval-log` / `--approval-sha`); no
    results-zip anchor (`--zip-sha`) or a zip hash different from the sent line; `--quick`; a non-default option not
    pinned by the approval file (pinned ones are listed as notes); no options recorded.
6. Draft tables for `FW_test_report_HG1`: per item the verdict and deciding checks, plus the operator-attested entries.

Exit code 1 if anything is listed.

## 5. Operator prompt style and pictures

- **One action per prompt:** `[ITEM KEY] what to do — what to look for`, with the expected value or unit. `abort` at
  any prompt stops the session safely (HALT to an identified device; BENCH-EXIT if the sense bypass may be fitted).
- **Safety first in the text:** the PSU state ("48 V PSU is OFF"), where the observer's hand is (red E-stop), "hands
  off" before a release / enable. Bypass steps (§6.8) name the tag and the restore step.
- **Measurements:** the point name (M-1…M-9, `{pin}-ILED`), the instrument range and the unit typed by the operator.
  Values are entered as numbers; anything else is asked again.
- **Plain language (GR-2):** the runner prints the plain text from `resources/prompts_plain.json` (`ITEM:KEY`, else
  `*:KEY`) first — who does what, what to look for, the picture to use — and the exact technical instruction below it
  as `details:`; the recorded prompt (results, `prompts.jsonl`) stays the technical text, so the analysis does not
  depend on wording. Answer lines: `-> press Enter when done`, `-> type the value in <unit>`, `-> type y (yes) or n (no)`;
  `abort` always works. The twin rehearsal covers 154 (item, key) prompts; every one of them has a plain text
  (`test_prompt_resources_are_consistent`; the remaining keys are board-only: FLASH, USB-OFF/ON, RC-*, READY, …).
- **Pictures:** printed as `picture: <path>` below the prompt, from `resources/pictures.json`; lookup order
  `ITEM:KEY`, `*:KEY`, `ITEM:*`; a value may list several pictures. Map (A's README v1.1):

| Picture | Prompts |
|---|---|
| B1 measurement header | JUMPERS, TAPS, all of HG-01, RC-ESTOP-2, RC-<input> / {START,END}-STIM (with B3), {START,END}-REAL |
| B2 multimeter points | M-1, M-2a, M-2c, M-3b, M-3c, M-4p, M-5, M-5iso, all of HG-16 |
| B3 J-STIM stimulus | P-3, P-4R, P-4V, P-6, P-8a/b/c, J-STIM, RC-ESTOP, RC-<input>, {START,END}-STIM |
| B4 HG-06 shunt | {PUL,DIR,ENA}-SHUNT / -RESTORE / -VOH / -ILED (HG-06 switches the 48 V OFF for the shunt changes) |
| B5 flashing | FLASH (every image step) |
| B6 MCU in reset, E-stop, D-42 NO wire | all of HG-10 c/d (M-points: B2), all of HG-17, VERIFY-ESTOP |
| B7 Nucleo RESET / power cycle | all of HG-14, HG-15 NRST / PWR, USB-OFF / USB-ON, VERIFY-NUCLEO |
| B8 spring and dial | all of HG-12, HG-15 dial readings, HG-25 dial / spring, all of HG-26, SPRING, VERIFY-CELL |
| B9 caliper reference | all of HG-09, HG-25 caliper / travel, all of HG-28, VERIFY-CALIPER |

- **Procedure corrections found while writing the plain texts (GR-2):**
  - HG-01 jumper resistances and HG-20 M-5iso are measured with the Nucleo **unpowered**: the runner closes the
    port, the operator unplugs the USB, measures, plugs it back, and the runner re-opens the same COM port and
    re-identifies the board (S-ID rules) before sending anything (`usb_off_block`).
  - HG-20 M-5 (+5V_CUT) needs the 48 V ON in phase 1: the runner asks for 48 V ON before and OFF after it.
  - HG-17 D-42 NO wire follows picture B6: wire change with the 48 V OFF, check with RESET held + E-stop
    pressed (still holds, R-10), refit with the 48 V OFF, then HG-10 c1 repeated and **recorded** (free again).
  - HG-15 USB power cycle: ≥ 5 s off (B7).

## 6. What stays operator-attested, bench facts to verify, design limits (D-57 d)

The runner records these answers with their time; Validator E can only check them for plausibility (consistency
with the FW events, photos):
- **Inspection:** board and solder bridges (HG-01, HG-20); DIP switches (S-00, HG-19); D-42 circuit inspection.
- **Mechanical state, felt by hand:** shaft free or holding (HG-07, HG-10 c, HG-17, HG-30 E-stop); spring fitted or
  removed; switch actuation.
- **Instrument readings:** DMM (M-1…M-9, HG-06 VOH / I_LED), caliper / dial indicator (HG-09, HG-15, HG-25, HG-26,
  HG-28), all typed in.
- **Physical actions** (PSU on / off, jumper changes, flashing, button presses on a cue): attested by the prompt
  answer. Where the FW sees the effect (ALM, ESTOP_OPEN, build string, LIMIT events), it is cross-checked
  automatically.

**Bench facts that A's pictures mark "ASSUMED — verify at HW gate" (GR3-2)** are asked at S-00 (after the DIP
question, before any motion), each with its picture:

| Prompt | Fact | Effect of the answer |
|---|---|---|
| VERIFY-ESTOP (B6) | E-stop contact-block terminal numbers: NC (sense → PA10) and NO (D-42 → R_E); pictures assume NC 11-12, NO 13-14 | recorded; the HG-17 NO-wire prompts refer to "its terminal" |
| VERIFY-NUCLEO (B7) | Nucleo part positions: B2 RESET, B1 USER, LD2, JP5 on U5V | recorded; "no" = the operator uses the board silkscreen |
| VERIFY-CELL (B8) | load cell on the START side: a +x move (away from START) pulls the spring (tension, +F) | **must be yes** — else S-00 FAIL, the session stops before motion (HG-12 / HG-15 preload direction) |
| VERIFY-CALIPER (B9) | two flat caliper reference faces chosen and marked (fixed face at the START end, the table's −x face) | **must be yes** — else S-00 FAIL (HG-09 / HG-25 / HG-28 readings) |

Accepted limits (D-57 d) and the Orchestrator's decisions on C's review:
- no live diagnosis, no on-the-spot finer repeat (INCONCLUSIVE → a second session);
- §6.8 bypass trials need a second person on site (observer at the red button and the PSU switch);
- a fabricated approval file is detected offline only (§3);
- **(a) revocation after issue:** the runner cannot see DECISIONS.md. If the PO revokes an approval after the file
  was issued, the PO tells the operator directly to stop; the file's validity window stays ≤ 7 days so a forgotten
  file expires by itself (runbook §3);
- **(b) tamper anchor of the results:** the runner prints the results-zip SHA-256 in large text at the end; the
  operator sends that line to the PO separately and immediately (e.g. in the message text). `hil_analyze.py
  --zip-sha "<line>"` checks it; a board zip analysed without it is a PROBLEM (C-GR-2).
